# 视频：方案

_2026-10-26 的设计稿；第 1 步（能放）、第 2 步（看得舒服）和第 4 步（配音）同一天实现了，见 [PROGRESS.md](../PROGRESS.md)。实现时有变化就改这里。界面稿在[设计画布](https://claude.ai/artifact/BNySHo46KNT4uv1j2oQXke)上
（8 个界面，私有，要在页面的 Share 里共享后别人才能打开）。_

## 要解决什么

- 很多人手里的材料是视频：从 YouTube 下载的、课程录像、剧集片段。现在只能先自己转成音频，画面（口型、表情、场景）也就丢了。
- [PRODUCT.md](../PRODUCT.md) 原来把视频放在“v1 不做”里；2026-10-26 决定做，先出这份方案。
- 不能破坏的：没有视频时一切照常；播放器的核心（解码、变速、循环、录音）不搬家；Mac 上现有的界面、文案和快捷键不变。

## 先定的几件事

| 问题 | 建议 | 理由 |
| --- | --- | --- |
| 声音和画面谁说了算 | **声音仍在 Rust 引擎**；画面是 WebView 里一个静音的 `<video>`，跟着引擎的位置走 | 变速保持音高、帧级 A–B 循环、跟读录音的 tap、转写、学习记录都不用改；画面交给 WebView 解码，有硬件加速，应用不用带视频解码 |
| 视频算什么 | **有画面的音频**：同一个列表，同一套字幕、录音、解释、学习记录，只多一块画面 | 进度、字幕、录音本来都按文件路径记，视频文件直接适用 |
| 播放控件放哪 | **只在底部播放条**；画面上只有悬停时出现的布局切换 | 一套控件、一套快捷键；画面上再放一套会和播放条打架 |
| 第一版支持哪些格式 | **mp4、m4v、mov**（画面 H.264，Mac 上还有 HEVC；声音 AAC） | symphonia 已经开了 `isomp4` + `aac`；WKWebView 和 WebView2 都能放 H.264 |
| 用不用 ffmpeg | **不用**（应用和插件都不用） | 现在两边都不依赖它；体积大、许可证麻烦 |

### 不选的做法

- **在 Rust 里解码画面**（ffmpeg / GStreamer）再送进 WebView：应用大几十 MB，许可证复杂，还要自己传帧。WebView 本来就会放视频。
- **让 `<video>` 自己出声**，引擎不管视频：变速保持音高、帧级循环、录音时抄一份输出都在引擎里，放弃它们等于重写播放器。
- **继续让用户自己转成音频**：画面丢了，正是要解决的问题。

## 界面

画布上的 8 个界面分三排：看、练、带进来。下面只写规则，样子看画布。

### 列表

- 视频和音频在同一个列表里，名字后面一个小胶片图标（13px、`text-faint`），右边照旧是“已听完”的勾或正在播放的跳动条。
- 放不了的视频（WebM、MKV）**也列出来**，名字灰掉、图标换成提示符号；点开在主区说明原因和办法（见“放不了的视频”）。不让文件“消失”。

### 看：三种布局

| 布局 | 什么时候 | 样子 |
| --- | --- | --- |
| 上下（默认） | 主区宽度 < 1100px | 标题缩成一行（22px），下面画面，再下面是句子列表。画面下有一条拖动条调高度（全局记住，最多占窗口一半高） |
| 并排 | 主区宽度 ≥ 1100px 时默认 | 左边画面，画面下是正在说的这句（24px，逐字亮），眼睛不用离开口型；右边是整份字幕 |
| 影院 | 按 `V` 或画面上的按钮 | 句子列表收起，只留画面、当前句、下一句（淡）。当前句可以藏起来，对应“不看字幕跟读”那一步。左侧列表不自动收起（和别处一样用 ⌘B），免得替人改了列表的开关 |

- `V` 在 上下 → 并排 → 影院 之间轮换（现在没有用到 `V`）。快捷键写进 `?` 表和 tooltip，不贴在按钮上。
- 选的布局和画面高度都是全局设置（像速度）；默认是“并排”，窗口窄到放不下时显示成上下，不改设置。`V` 只在放得下的布局之间轮换。
- 没有字幕时（循环面板那一页），画面放在循环面板上面，其余不变。

### 播放设置里的「画面」

只在当前是视频时出现，放在速度下面：

- 画面：在上 / 并排 / 影院 / 不显示（四个图标的分段选择器；应用里没有开关控件，开和关都用分段选择器）。
  不显示时没有 `<video>`（不解码），和音频一样；练“只听不看”时用。
- 遮字幕：不遮 / 遮住（见下）。

### 遮住烧录字幕

- 下载的视频常把字幕烧在画面里，跟读时会忍不住看。打开后画面下方盖一条模糊带（`backdrop-filter: blur`），上下边可以拖。
- 位置是全局记的（`maskTop` / `maskBottom`，画面高度的比例）：同一类视频的字幕位置差不多，不必每个视频调一次。默认盖住画面的 74%–96%。
  拖上下边改宽窄，拖中间整条移动；不会比画面高度的 5% 更窄。

### 循环、跳句

- 和现在一样：`S` 循环当前句、`[` `]` 换句、`L` 设 A–B。画面跟着跳，不另做什么（见“画面跟着声音”）。
- 句子行、循环条、播放条里的 A–B 都不变；橙色仍只表示“正在循环”。

### 配音（第 4 步）

- 跟读录音多一种方式：听完再说 / 边听边说 / **配音**。放画面、**不放原声**，跟着口型说。
- 句子照原声的时间一个字一个字亮，当提示（没有字时间的字幕整句亮）。
- 录完和现在一样自动保存。回放多一个「配音」：画面 + 你的声音，像给这段配了音；原句 / 我的 / 对比照旧，两条波形照旧。
- 卡片上说“比口型晚 0.18 秒”：和边听边说的跟读延迟同一种算法（`record/take.rs`），比的是原声开口和你开口的时间。
- 只有视频才有这个选项。第一步也可以只做“录音时画面静音跟着放”，配音回放以后再加。

### 放不了的视频

- **整个放不了**（WebM、MKV：声音是 Opus 或容器不认识）：列表里灰掉；点开在主区说明“这个视频放不了”、为什么、怎么办（用「从链接导入」重新下载成 mp4，或用 HandBrake 之类的工具转成 mp4），按钮“从链接导入…”。（“在访达中显示”第 1 步没做：要多一个命令，先看有没有人需要。）
- **画面放不了、声音能放**（例如 Windows 上没装 HEVC 扩展）：照常播放，画面区换成一句说明，其余功能都在。由 `<video>` 的 `error` 事件判断。
- **mp4 里只有声音**：当音频处理，不显示画面区。打开后看 `videoWidth` 是不是 0。

## 技术方案

### 声音：几乎不用改

- `audio/decode.rs` 的 `Decoder::open` 已经挑“第一条有采样率的轨”，就是音轨；播放、转写（`transcribe/pcm.rs`）、切原句（`record/original.rs`）都经过它，所以 mp4 的声音在这几处一起能用。
- `library.rs`：`AUDIO_EXTENSIONS` 加上 `mp4`、`m4v`、`mov`（改名 `MEDIA_EXTENSIONS`），`Track` 多一个 `video: bool`（按扩展名；`m4a` 永远不是）。WebM、MKV 也扫出来，但标成放不了。
- 字幕、进度、录音、解释、学习记录都按路径，不用改。旁边的同名 `.srt` / `.vtt` 照样自动读入。
- 要验证：
  - symphonia 的 `isomp4` 在视频轨排在前面、`moov` 在文件末尾时能不能打开。
  - YouTube 下载的 mp4 能不能打开；跳转快不快：大文件里 `seek` 要查样本表，看看 1 GB 的文件慢不慢。

### 文件交给 WebView

- 应用里一个只给自己用的小 HTTP 服务（`media.rs`，只用标准库）：
  - 只听 127.0.0.1，端口随机；地址里带一个每次启动新生成的口令（128 位），还核对 `Host`。地址在 snapshot 的 `mediaBase` 里交给前端。
  - 路径经过 `AppState::allowed`（`resolve_inside`），而且只给视频：用户选的文件夹（和示例）里的，和别的命令一样。
  - 支持 `Range`（206），边读边发，不把整个文件读进内存；WebView 看够了会断开。
  - CSP（`tauri.conf.json`）的 `media-src` 只多了 `http://127.0.0.1:*`。只听本机，所以 Windows 防火墙不会问。
- 原来的设计是自定义协议（`media://`），实现时试过、放弃了：WebKit 经自定义协议读视频是一帧一个请求（几十到几百字节），
  每个都要跨进程到应用再回去。smoke 里量到画面只能放到实时的 0.87 倍，两个视频同时读时会停住，跳转也会卡死。
  改成同步回答好一点（0.95 倍），换成本机 HTTP 后 WebKit 自己的媒体栈大块地读，正好 1.00 倍。

### 画面跟着声音

- 前端一个纯函数（`lib/videoSync.ts`，带测试），每 50 毫秒算一次（用定时器，不用 `requestAnimationFrame`：窗口被挡住时动画帧会停，
  画面在重新露出来时应该已经对上）：
  - 目标位置 = 最近一次 `player:status` 的 `time`，播放中再加上收到它以来过的时间 × 速度（`player:status` 约 30Hz，中间要补）。
  - **只靠跳来纠正，不改速度**：
    - 差 > 0.1 秒：跳，而且往前多跳一点（`lead`），落地时正好对上。`lead` 从每次落地后第一次检查时还差多少来调（落在后面就加，落在前面就减）。
      跳完给 1 秒稳住，期间不再跳；声音自己动了（循环跳回、往后跳，按每次检查时声音是不是在它该在的地方判断）就马上跳。跳了 2 秒还没落地就再跳一次。
    - 速度只在你改速度时改，而且和一次跳一起做。
  - **关掉 `<video>` 自己的音轨**（`audioTracks[i].enabled = false`，有音轨出现就关）。这是让画面跟得上的关键。
  - 实现时在真实应用里一帧一帧记下来（smoke，窗口露着）才找到的两件事：
    - WebKit 在播放中改 `playbackRate` 时，画面先跳回上一次跳转的位置，再停住半秒左右。所以最初的“快慢 5% / 10% 追上”都是越追越乱。
    - 视频里有音轨时（就算静音），每次跳完约 0.55 秒画面会再停 0.4 秒（AVFoundation 要重新对齐那条音轨），跳转本身也要 0.1–0.35 秒。
      画面一停就落后，过一秒又跳，又停……关掉音轨后，跳转 50 毫秒内落地，之后不再停。
    - 改了以后：204 次检查里画面没有停过，只跳了 6 次（开始、改速度、往后跳、循环跳回），稳定时差 0.02–0.07 秒。
  - 暂停：`pause()` 并跳到准确的那一帧（差 > 0.04 秒）。
  - 窗口被别的窗口挡住（页面 hidden）：画面停下、不解码（只听的时候省电），露出来的那一刻再对上。被挡住时 WebKit 把定时器放慢到约每秒一次，
    画面也会卡，硬要对是白费功夫。
  - 声音比画面长：停在最后一帧（视频放到头再叫它播放会从头开始）。
- 速度：`playbackRate` = 引擎速度（0.5–2.0，两种 WebView 都支持）；画面静音，所以不涉及音高。
- A–B 循环和句子循环：引擎越过 B 时在音频回调里跳回 A，`time` 往回跳一大截，按上面的规则就是一次跳转。
  - H.264 跳到非关键帧要从前一个关键帧解起，YouTube 的视频约 2–5 秒一个关键帧。测试视频上（关掉音轨后）跳转 50 毫秒内落地，所以一个 `<video>` 够用；
    真实视频上如果跳回时画面卡，再考虑放两个，备用的那个先停在 A。
- 录音、回放录音时的画面：
  - 听完再说：放原句时画面跟着；轮到你说时画面停在这句结尾。
  - 边听边说：跟着放。
  - 回放录音：回放里放原句的那段画面跟着走，放“你”的那段停住。`recorder:clip` 事件已经带 `secs`。
- `Status.time` 是“现在听到的位置”。要验证：蓝牙耳机自己的延迟引擎知不知道（AirPods 约 0.15–0.25 秒）。不知道的话，画面会比声音早，可能要一个“画面延后”的设置，或按输出设备记一个偏移。

### YouTube 插件

- 插件协议：`files` 里的 `kind` 多一个 `"video"`；`plugins/accept.rs` 现在只收 `"audio"`，改成也收 `"video"`（同样检查文件，按扩展名和 `Decoder::open` 能不能打开）。[plugin-dev.md](plugin-dev.md) 跟着改。
- 确认框多两行：内容（只要声音 / 声音 + 画面，默认只要声音，记住上次的选择）、清晰度（480p / 720p / 1080p，默认 720p），旁边写大约多大（yt-dlp 给的 `filesize` / `filesize_approx`）。
- 下载：分别下画面 `bestvideo[ext=mp4][vcodec^=avc1][height<=720]` 和现在的 `bestaudio[ext=m4a]`，**在插件里合成一个 mp4**：两个 ISO-BMFF 的样本表合进一个 `moov`、数据放进一个 `mdat`，不转码。合成出来的是普通 mp4，在访达里也能直接看。
- 这是最大的未知，先单独做一个原型。可能用 `mp4` crate（读写都有），YouTube 的 DASH 文件是分片的（`moof`），要看它读不读得了。走不通时的退路：
  - 第一次选“声音 + 画面”时下载 ffmpeg（像 yt-dlp 一样固定版本 + SHA-256），让 yt-dlp 自己合。但 macOS arm64 没有官方的静态版本，来源不好定。
  - 用 360p 的合成格式（itag 18，自带声音）。画质低，YouTube 也可能不再提供。

### Windows

- WebView2 能放 H.264；HEVC 要装“HEVC 视频扩展”，没装时走“画面放不了、声音能放”。
- 自定义协议的地址见上；“在访达中显示”说成“在资源管理器中显示”。
- 浏览器 mock 里用 `?platform=windows` 看一遍。

## 分步

每一步一个可以体验的提交，提交前 `npm run check`，用户可见的变化写进 CHANGELOG。

1. **能放**（2026-10-26 已实现）：列表认 mp4 / m4v / mov；本机视频服务和 CSP；上下布局和拖动条；画面跟着声音（播放、暂停、跳转、变速、A–B 循环、句子循环、换句）；只有声音的 mp4 当音频；放不了的视频列出来并说明。
   - 自动验证：`videoSync` 的规则；扩展名和 `video` 标记；协议的 Range 解析和越界路径被拒。
   - smoke：`scripts/make-fixtures.sh` 用 ffmpeg 生成一个带画面的 mp4（`testsrc` 画面 + `say` 的声音），检查能放、能转写、能循环一句。
   - 浏览器 mock：mock 后端给一个小的示例视频。
   - 需要人试：画面和声音对不对得上（扬声器、有线耳机、AirPods），循环跳回时画面卡不卡。
2. **看得舒服**（2026-10-26 已实现）：并排、影院、`V`；播放设置里的「画面」；遮字幕；隐藏画面。
3. **带进来**：YouTube 插件的“声音 + 画面”（先做合成 mp4 的原型）；插件协议的 `"video"`；`accept.rs`；`plugin-dev.md`。
4. **配音**（2026-10-26 已实现）：录音方式“配音”（引擎照常走但不出声）；回放「看配音」；“比口型晚多少”。
   做法：引擎多一个 `Cmd::Mute`，在抄给录音线程之后才把送给声卡的变成静音，所以录音照样有原句，做法和边听边说一样（左原句、右你，测得出晚多少），
   只是不去回声（喇叭没出声，去回声只会压低你的声音）。抄给录音线程的每一块多记一个“在音频里的位置”（`Mark::src`），
   录音存下原句在音频里从哪开始（`original_at`）；回放边听边说或配音的录音时，画面按 `original_at` + 录音里的时间 × 录音时的速度走。
   听完再说的录音回放时画面不动（你的那段没有对应的画面）。

## 待定

- 配音做不做、什么时候做。
- 默认布局：现在的建议是按主区宽度自动选上下或并排。
- 布局、画面高度、遮字幕的位置是全局记还是按视频记（现在都是全局）。
- YouTube 的默认清晰度（建议 720p：一集 10 分钟约 100 MB）。
- WebM：以后加 Opus 解码（libopus，是 C 依赖），WebM 的声音就能放；画面 VP9 两种 WebView 都能放。MKV 不打算支持。
- 蓝牙耳机的延迟要不要单独处理（见“画面跟着声音”）。

## 合成 mp4 的原型（结论）

2026-10-26，代码在 `plugins/youtube/src/mux/`（还没接进导入）。**能做到**：插件里不用 ffmpeg、不转码，把分别下载的画面和声音合成一个普通 mp4，上面的两条退路都不需要。

- 下下来的是什么：两个文件都是分片的 DASH（`moov` 里样本表是空的、带 `mvex`，后面是 `sidx` 和一串 `moof` + `mdat`；画面约 5 秒一片，声音约 10 秒一片）。
  画面有一条编辑表（`elst` 的 media_time 512 或 1024，跳过 B 帧的延迟），声音没有。
  电脑上装了 ffmpeg 时 yt-dlp 会自己把 m4a 改成普通 mp4（FixupM4a），所以试的时候要把 ffmpeg 从 PATH 里拿掉，和应用里跑插件时一样。
- 做法：自己读写盒子，不加依赖（`mp4` crate 把 `moov` 写在文件末尾、不写编辑表、会重写 `stsd`，不合用）。
  读：分片的和普通的都认；每个 track 的 `hdlr`、`vmhd` / `smhd`、`dinf`、`stsd`（含解码设置）原样复制，样本变成一张表（位置、大小、时长、合成时间偏移、是不是关键帧）。
  写：`ftyp`、一个 `moov`（画面是 track 1，声音是 track 2；`stts` / `ctts` / `stss` / `stsc` / `stsz` / `stco`，超过 4 GB 用 `co64`），然后一个 `mdat`，样本按播放时间约半秒交错。
  编辑表保留（时长换成新的 1000 时间刻度）；片与片之间有空档时前一个样本补长；第一片不从 0 开始时补一个空编辑。
- 试了 3 个真实视频（19 秒 240p、3.5 分钟 720p、11.6 分钟 720p）：
  - 每个包的时间、时长、大小、关键帧都和 ffmpeg 自己 `-c copy` 合成的一样，包的内容（md5）也一样。
  - AVFoundation（QuickTime Player 用的）：能放，所有画面帧和声音都解得出来，按帧精确跳到开头、中间、末尾都对。
  - WKWebView（Safari 的引擎）的 `<video>`：能放，跳到中间、末尾、开头后接着放；用 Web Audio 量到了声音；截图画面正常。
  - 应用的解码器（symphonia 0.5、`isomp4` + `aac`，和 `audio/decode.rs` 一样取第一个有采样率的 track）：跳过画面、打开声音，解出的帧数和单独的 m4a 一样，跳转正常。
  - 没有在 QuickTime Player、Safari 里人工看和听；画面和声音对不对得上没有用耳朵确认（只确认了时间和 ffmpeg 合成的一致）。
- 快、省内存：11.6 分钟 720p（画面 90.5 MB + 声音 11.3 MB → 101.6 MB）合成 45–80 ms（文件在磁盘缓存里）；整个测试进程（合成，再把声音解两遍）峰值内存约 6 MB。
  样本一块一块复制，内存里只有样本表（这个视频约 5 万个样本，`moov` 290 KB）。合成时磁盘上要暂时多一份。
- 限制：
  - 每个文件只取第一个画面 / 声音 track 和一个 `stsd` 条目；加密的（`encv` / `enca`）不管。YouTube 的文件都不是这些情况。
  - 声音的 AAC 前置延迟和以前一样不裁剪（ffmpeg 合成的也不裁：声音的编辑表从 0 开始）。AVFoundation 自己去掉 2112 个样本（约 48 ms），symphonia 不去，
    所以在应用里画面跟着引擎走时，画面可能比声音早 23–48 ms。比人能察觉的声音落后（约 125 ms）小，做“画面跟着声音”时可以考虑减掉。
- 接进导入时：一次 yt-dlp 用 `-f "bestvideo[ext=mp4][vcodec^=avc1][height<=720][protocol=https],bestaudio[ext=m4a]"`（逗号：两个格式各存一个文件；
  `protocol=https` 保证是试过的 DASH 文件，不是 m3u8），然后 `mux::merge` 合成 `video.mp4`、删掉两个原文件；进度用它的回调，取消时回调返回“已取消”，写了一半的文件会删掉。
- 测试：`cargo test`（在 `plugins/youtube`）里有不联网的单元测试（照 YouTube 的样子造的小 DASH 文件，加 `fixtures/` 里 ffmpeg 生成的两个小文件，用 symphonia 打开）；
  真实视频：`SHADOWING_URL=<链接> cargo test --release real_mux -- --ignored --nocapture`（说明在 `src/mux/real_tests.rs` 开头）。
